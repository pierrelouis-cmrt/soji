## Additional findings beyond the supplied baseline

### P1: failed permanent cleanup rollback overwrites newly recreated user data (open; independent fixture)

Independent review supplied `/tmp/soji-rollback-audit.py`; its source was inspected here without execution. The reviewer reports an isolated actual-filesystem reproduction: `Cleaner.move(..., want_permanent=True)` stages `cache.bin` containing old disposable cache; the journal append at phase `removing` is injected to recreate `cache.bin` with `NEW UNIQUE USER DATA` and raise an I/O error. Cleanup returns failed, but the original path then contains old cache and the new unique data is gone.

The failure path is explicit: `soji_cli/cleanup.py:381` stages the old target; `:385` appends the checkpoint before setting `removal_started=True`; `:408`–`:410` rolls back with `os.rename(staged, original)` if that append fails. Rename can overwrite a concurrently recreated file at the original path. The original identity check does not authorize overwriting a different file created later. Trigger: permanent filesystem cleanup, pre-removal failure after staging, and concurrent original-path recreation. TUI Trash-only X does not enter this branch. No original journal entry is attributed to this permanent-path bug.

Priority: use an atomic exclusive/no-clobber rollback, not an existence-check followed by ordinary rename. If the destination exists or exclusive rollback is unavailable, preserve the staged file and new destination; record the conflict, staged location and failure without claiming rollback succeeded. Regression: inject the reported journal failure and original recreation; assert new bytes survive, old staged bytes survive and conflict metadata is recorded. Also cover normal successful rollback, directory/file destination conflicts and rollback failure. This is a release-blocking data-loss path even when the cleanup itself reports failure.

### P1: ignored worktree data can be permanently deleted (fixed on `fix/worktree-data-safety`; independent fixture)

Independent review supplied `/tmp/soji-independent-audit.py`; its source was read here, not executed. The reviewer reports a real local disposable Git reproduction: a detached, merged and pushed worktree contains `.gitignore` with `local-data/` and a unique `local-data/irreplaceable.txt`. `GitInspector.inspect(worktree=True)` reports verified, clean, merged and pushed; `Cleaner.tool_action(git-worktree)` then removes the worktree and unique ignored file without `--force`.

Source supports the mechanism: `soji_cli/gitstate.py:16` uses `git status --porcelain --untracked-files=normal`, which does not inventory ignored files. `soji_cli/cleanup.py:419` repeats that guard, then `:421` invokes `git worktree remove`. The normal apply path requires explicit tool/permanent flags (`cleanup.py:316`); the TUI excludes this action. Those gates do not make ignored files reproducible or backed up. Impact is permanent loss outside Trash, even when commits are safely merged/pushed.

The strengthened fixture uses the recognized `~/.codex/worktrees/audit` path aged 30 days. The reviewer reports that a full Scanner selects it with no holds in **careful, balanced and aggressive**, before the real tool action deletes the unique ignored file. This is an eligibility failure in all modes; actual permanent execution still requires the explicit tool/permanent flags and is excluded from TUI Trash-only X.

Priority: block automatic worktree removal when ignored content has not been positively classified as disposable; inspect ignored and untracked contents, fail closed on incomplete enumeration, and avoid treating Git cleanliness as filesystem safety. Regression: disposable local repository/bare remote/worktree, unique ignored file, verify guard refusal and file survival through the actual tool boundary; retain a positive empty/known-safe worktree case. No original journal plan is attributed to this bug: the supplied journal contains Trash operations, not a witnessed worktree tool deletion.

Fix: `GitInspector.inspect(worktree=True)` inventories ignored entries from the worktree root (`git ls-files -z --others --ignored --exclude-standard --directory --no-empty-directory`, 20 s timeout). Only `node_modules/`, `__pycache__/`, `.pytest_cache/`, `.mypy_cache/`, `.ruff_cache/`, `.DS_Store` and `*.pyc`/`*.pyo` entries count as disposable; any other entry, a failed/timed-out/unterminated/possibly truncated inventory, or a path that is not the worktree root, holds the row in every mode. `Cleaner.tool_action` re-inspects immediately before `git worktree remove` (still no `--force`) and also requires `contentsVerified`. Regressions: `tests/test_worktree_ignored.py`; corpus rows `~/.codex/worktrees/data` (held) and `~/.codex/worktrees/safe` (selected).

Regression: the reported scan→plan→new pin→fresh/apply sequence, assert refusal and version survival, plus existing-pin and removed-pin cases under a controlled complete scope. This is a verified independent fixture finding, not a witnessed cause of any original journal entry.

### P1: confirmation hid selected paths and its final safety text (fixed)

Before this change, `soji_cli/tui.py`'s `modal` (HEAD lines 309–345) clipped content to terminal height, replacing the remainder with “more lines.” There was no modal scroll handler; pressing an arrow cancelled confirmation. `cleanup_targets` (now line 59) includes every eligible item in the current view when none is marked, while confirmation still authorized the entire target list. A large selection could therefore be approved without any way to inspect most of its paths inside confirmation. The undo guidance at the bottom was also hidden.

Journal context: `046cd366` contains 1,370 entries and `0ea353e2` 112, including the runtime and extension paths below. Those sizes demonstrate why pagination matters, but the journal does not prove which UI initiated those plans.

Fix: wrap then scroll all confirmation/result content; arrows, J/K and Page Up/Down preserve the pending confirmation. Warnings precede paths. Current implementation: `soji_cli/tui.py:50`, `:339`, `:701`, `:752`. Tests: `SafetyWarnings.test_long_confirmation_can_reveal_every_path_and_final_warning`, plus mocked curses flow exercising Page Down/Page Up before Y.

### P2: completion claimed Trash bytes were freed (fixed wording)

HEAD `soji_cli/tui.py:706` displayed “freed” using the sum of journal sizes from `clean_targets` (now `:87`). This does not measure free-space gain. Moving to same-volume Trash normally retains the data until deletion, and reclaimable allocation can differ further due to links/clones. A misleading gain claim can encourage repeated cleaning or emptying Trash before validating software.

Trigger: any successful TUI Trash batch; all five journal plans contain completed moves, though their initiating UI is unknown. Fix at `soji_cli/tui.py:728`: report bytes moved and explicitly state that space may remain occupied. The internal `freed` result key is retained for compatibility; it is not a free-space measurement. Mocked curses regression rejects the previous “freed.” message.

### P2: completion's advertised undo key was consumed by the panel (fixed instructions)

HEAD `soji_cli/tui.py:720` said “Press U to put this batch back,” but its result-panel key handler (`:741` then, `:773` now) cleared the panel and continued before reaching the undo handler. One U did not restore anything. This applies to every completed TUI batch and could leave a user mistakenly believing undo had run. No journal entry proves the user pressed U.

The completion text now explicitly says to close the panel, then press U to **attempt** undo. The panel prominently explains the surviving-Trash requirement. It does not promise that identity/parent checks will allow restoration. Mocked curses tests verify completion warning placement; existing fake-home tests verify actual cleanup/undo through Cleaner.
